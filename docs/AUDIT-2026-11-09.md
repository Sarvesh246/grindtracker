# GRIND audit and fix plan (2026-11-09)

Audited at commit `5a6215e` on `main`. This file is written for the agent that
will do the fixes: every item says what is wrong, where, why it matters, how to
fix it, and how to prove the fix. Nothing in the codebase was changed by the
audit.

## How to use this plan

- Read `CLAUDE.md` and `AGENTS.md` first. Next.js here is 16.x; check
  `node_modules/next/dist/docs/` before touching Next-specific code.
- Work top to bottom. Phase 0 restores the safety net, so do it before anything
  else; later phases assume CI is green.
- One commit per numbered item, straight to `main` (repo convention). Commit
  messages explain the why.
- None of these fixes needs a SQL migration. If you find yourself writing one,
  stop and re-read the item.
- Gate for every commit:

  ```bash
  npm run lint
  npx tsc --noEmit
  npm test
  NEXT_PUBLIC_SUPABASE_URL=https://example.supabase.co NEXT_PUBLIC_SUPABASE_ANON_KEY=placeholder npm run build
  ```

- Items marked **CONFIRMED** were traced in the code. Items marked
  **PLAUSIBLE** follow from the code but the trigger was not reproduced;
  reproduce before fixing.

## Phase 1: correctness bugs

### 1.1 A set the server will never accept is treated as "offline" and blocks Finish (CONFIRMED, medium)

`ActiveWorkout.tsx`: `runWithRetry` (line 123) retries every error three times,
and every write path (`handleCheck` ~1054, `handleSaveEdit`, `persistSetMeta`,
skip/unskip, delete) then calls `queueOp` and shows "Saved on this device —
will sync once back online". `handleFinish` (2526–2531) and
`HomeDashboard.handleSaveActive` (585–589) refuse to finish while the queue is
non-empty.

A rejection that is not a network failure (a CHECK violation, an RLS denial, a
guard trigger) can never sync. Concrete trigger: `session_logs_weight_sane`
allows 0–2000 lb and `session_logs_reps_sane` 0–1000 (`docs/sql/10`), and the
weight/reps inputs have no upper bound, so a typo such as `1000` in kg mode
(2204 lb) is checked optimistically, queued, reported as an offline save, and
Finish then answers "Still syncing sets" indefinitely. The user can recover
only by guessing that the set must be edited.

Fix:
1. Add `isTransientError(error)` beside the queue code
   (`src/lib/utils/offlineQueue.ts`). Transient: a thrown fetch `TypeError`,
   no Postgres `code`, HTTP 5xx / 408 / 429, an expired-JWT response. Permanent:
   any error carrying a Postgres `code` (`23xxx`, `42501`, `P0001`, ...).
   Read how `@supabase/postgrest-js` shapes errors before choosing the fields.
2. `runWithRetry`: return immediately on a permanent error.
3. Write paths: on a permanent error do not queue. Revert the optimistic state
   for that set (uncheck it), and show a message that names the problem.
4. `flushQueuedOps`: drop an op that fails permanently, `reportError` it, and
   return it in a second list so the caller can un-check the row.
5. Clamp at the input: reject weight above 2000 lb (after `fromDisplay`) and
   reps above 1000 before the optimistic commit, in `handleCheck` and
   `handleSaveEdit`.

Tests: unit tests for `isTransientError` and for `flushQueuedOps` with a fake
client (transient stays queued; permanent is dropped and reported).

### 1.2 A failed exercise read shows "NO EXERCISES FOR THIS DAY" (CONFIRMED, medium)

`ActiveWorkout.tsx` 488–495: `const { data: allExsData } = await
supabase.from('exercises')...` discards the error, so one dropped request
renders the empty-day screen telling the user to add exercises. This is the
"failed read is not an empty account" rule from `CLAUDE.md`, missed here.

Fix: destructure `error`; on error show a "Couldn't load this workout" state
with a RETRY that calls `initSession` again (reuse the pattern and copy of the
Home stats-unavailable card). Wrap the body of `initSession` in `try/catch` so a
thrown request cannot leave `loading` true forever.

### 1.3 Home quick-save cannot recover from a lost response (CONFIRMED, medium)

`HomeDashboard.handleSaveActive` (575–644) calls `complete_session` once, with
no retry and no `SESSION_NOT_OPEN` handling. If the write commits but the
response is lost, the user sees "Could not save workout", the resume banner
stays (no refresh on the error path), and every further tap fails with
`SESSION_NOT_OPEN`. `ActiveWorkout.handleFinish` (2556–2641) already handles
exactly this.

Fix: extract the finish sequence into one helper (suggested:
`src/lib/utils/completeSession.ts`) that does the retry, treats
`SESSION_NOT_OPEN` as success and re-reads the result, advances the rotation,
writes the undo token and awards badges. Call it from `handleFinish`,
`handleSaveActive`, and `DaySelect` (line ~254, which has its own copy).
`markAppDataStale('/home')` and `router.refresh()` in the Home error path too.
Keep `NO_WORKING_SETS` surfaced to the caller.

### 1.4 The proxy sends an established user to `/setup` when one read fails (CONFIRMED, medium-low)

`src/proxy.ts` 96–104: `const { data: profile } = ...maybeSingle()` drops the
error, and `!profile` redirects to `/setup`. It only runs when the
`grind_profile_ok` cookie is absent (new device, cleared cookies, expiry), which
limits how often it bites.

Fix: read `error` too. On error, let the request through without setting the
cookie (RLS still bounds every read). Redirect only on a successful read that
shows no row or no `setup_completed_at`.

### 1.5 Profile renders level 1 / zero streak when the stats read fails (CONFIRMED, medium-low)

`src/app/(app)/profile/page.tsx` 101–108 falls back to `level: 1` and zeros,
directly under a comment that says a missing `user_stats` row is a failed read.
The same applies when the whole `Promise.all` rejects (81–84).

Fix: pass `statsUnavailable` to `ProfileDashboard` and render the same
"couldn't load your stats" + RETRY treatment Home uses, with the
`grind_last_stats` cache (`src/lib/cache/lastKnownStats.ts`) as the first
fallback. Wrap the badge, PR-count and set-count reads in `readWithRetry`.

### 1.6 The Coach's context swallows read errors, then caches the result (CONFIRMED, medium)

`src/lib/coach/buildContext.ts` ~270–371 runs about eighteen reads and takes
only `data` from each. A dropped `exercises`, `user_stats` or `sessions` read
produces a context that says the user has no days or no history;
`chat/route.ts` 308–318 then caches that JSON, so the wrong answer persists for
the cache lifetime.

Fix: destructure `error` for the reads the Coach reasons from (`user_stats`,
`exercises`, both `sessions` reads, `user_rotation`, rest days) and throw if any
failed. The route already refunds the message and returns 500 on a throw
(319–329), so no route change is needed. Optional reads (photos, friend
profile, notification prefs) may stay best-effort. Add a unit test with a fake
client where the `exercises` read errors.

Minor, same file: `loadRotationState` (line 383) repeats four of the reads
already made above. Resolve from the rows in hand with `resolveRotationIndex`.

### 1.7 Applying a workout template is not atomic; a retry can duplicate exercises (PLAUSIBLE, medium-low)

`src/lib/utils/applyWorkoutTemplate.ts` 41–58 runs three writes in parallel and
returns a single error if any fails. `exercises` has no unique constraint, so if
the exercise insert succeeded and another write failed, tapping again in the
setup wizard (`WorkoutStep.tsx`) inserts the whole template a second time.

Fix: make it idempotent without a migration. First read existing `day_type`s for
the user and insert only days that have no exercises yet; then upsert
categories; then write the rotation. Sequential, exercises first.

## Phase 2: rule violations and hardening

### 2.1 Two rotation writers bypass `rotationStore` (CONFIRMED, low)

`CLAUDE.md` says every pointer write goes through
`src/lib/utils/rotationStore.ts`. Two do not:

- `WorkoutManager.persistRotation` (580–606)
- `executeCreateDay` in `src/lib/coach/actions/createDay.ts` (287–316)

Both upsert `current_index` from a copy read earlier and set `updated_at` to
now. Two consequences: a stale index can overwrite a newer one (mostly healed by
the `current_day` anchor), and bumping `updated_at` disables the catch-up rule
in `resolveRotationIndex` (rotation.ts 206–210), so a finish whose advance never
landed is forgotten after any reorder.

Fix: add `writeRotationSequence(supabase, userId, mode, sequence)` to
`rotationStore.ts` that changes only `mode` and `sequence` (update the existing
row; insert with `current_index: -1`, `current_day: null` when there is none),
leaving `current_index`, `current_day` and `updated_at` alone. Grep for other
readers of `user_rotation.updated_at` first; if anything needs it to mean "row
last changed", stop and report instead. Use the new function in both places.

Also: `chipHints.ts` (33–36) and `startWorkout.ts` (35–38) select
`mode, sequence, current_index` for their fallback path; add `current_day,
updated_at` so the fallback resolves the same way as the primary path.

### 2.2 Coach confirm route can strand a proposal in `confirmed` (CONFIRMED, low)

`src/app/api/coach/actions/route.ts`: `createServiceClient()` (line 117) runs
after the proposal is claimed (94–99) and outside the `try`. If
`SUPABASE_SERVICE_ROLE_KEY` is missing it throws, the mutation never runs, and
the proposal stays `confirmed`, which the route then answers with 409 forever.

Fix: create the service client before the claim and return 503 if it throws.
Also return 422 instead of 500 when `executeConfirmedPayload` returns
`ok: false` (231–234); that is a refused action, not a server fault. Check how
`CoachProvider.tsx` reads the status code before changing it.

### 2.3 Chat history is taken from the client with no total size cap (CONFIRMED, low)

`chat/route.ts` `sanitizeHistory` (92–107) accepts up to 12 messages of up to
12,000 characters each from the request body, including `assistant` turns.
That is roughly 144k characters of model input per request, chosen by the
caller. The per-user rate limit bounds the count of requests, not their size.

Fix: cap the combined history length (drop oldest turns past a budget; pick the
budget from what `planCoachTurn` already assumes). Run `npm run coach:eval`
before and after, per `CLAUDE.md`. Loading history from `coach_messages` by
`conversationId` would be stricter but is a larger change; note it, do not do it
here.

### 2.4 `'unsafe-eval'` is in the production CSP (CONFIRMED, low)

`next.config.ts` line 24. React needs `eval` in development only.

Fix: include `'unsafe-eval'` only when `process.env.NODE_ENV !== 'production'`.
Verify with a production build and `npm start`: load `/`, `/login`, `/home`,
`/progress` (Recharts) and the Coach, and confirm the console shows no CSP
violations.

### 2.5 `supabase/migrations/` is a partial, drifting mirror of `docs/sql/` (CONFIRMED, decision needed)

`docs/sql/` holds 02–56. `supabase/migrations/` holds only 20, 21 and 27–51;
46 and 51 differ in content from their `docs/sql` copies (wrapped in
`begin/commit`, header lines changed). `docs/SQL.md` describes the folder as
"tracked copies" for `supabase db push`, which would build an incomplete schema.

This is the owner's call; do not pick silently. Options: delete
`supabase/migrations/` and the sentence in `docs/SQL.md`; or generate the mirror
from `docs/sql/` with a script and check it in CI. Ask before acting.

### 2.6 Silent failures (CONFIRMED, low)

- `FriendsAccordion.tsx` 274, 281, 288: `friendships` deletes ignore the result.
  Check `error`, toast on failure, and only then reload.
- `HomeDashboard.confirmRestBanner` 456: `refresh_stats` result ignored before
  the "Streak saved" toast. Check it; on error fall through to the failure toast.
- `DaySelect.tsx` 155–170: one count query per open session, in sequence. Use
  the single `in()` query `home/page.tsx` already uses (131–140).
