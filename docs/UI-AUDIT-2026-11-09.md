# GRIND UI/UX audit and fix plan (2026-11-09)

Audited at commit `3b0c988` on `main`. Companion to `docs/AUDIT-2026-11-09.md`
(correctness and security); this file covers how the app looks and feels.
It is written for the agent that will do the fixes: every item says what is
wrong, where, why it matters, how to fix it, and how to prove the fix. Nothing
in the codebase was changed by the audit.

## Read this first: how much of this was actually seen

GRIND is Google-sign-in only and sign-in does not work on localhost, so the
signed-in app was **never rendered** during this audit.

| Area | How it was checked |
| --- | --- |
| Landing `/` and `/login` | Rendered in a browser at 1440, 768 and 375 wide, dark and light, with measured contrast and tap-target sizes |
| Every signed-in screen | Source only: `globals.css`, the JSX, and scripted scans for small targets, small text, missing labels and colour misuse |

So each item carries a tag:

- **MEASURED**: a number computed from the token values or measured in the
  browser. Trust it.
- **CONFIRMED**: read directly in the source at the cited line.
- **PLAUSIBLE**: follows from the source, but needs eyes on the rendered
  screen before and after. Do not report these as fixed without a screenshot.

Line numbers are from the audited commit and will drift; search for the quoted
code if a line does not match.

## How to use this plan

- Read `CLAUDE.md` and `AGENTS.md` first. The Design System, Theming, Reduced
  motion and Motion system sections are binding. In particular: lime `--accent`
  is a fill and never a text colour, use `--accent-text` for text; reach for the
  five motion primitives before writing an animation; animation fill mode is
  `backwards`, never `both`; check every new class name against Tailwind's
  utilities before adding it.
- One commit per numbered item, straight to `main`. Messages explain the why.
- Phases are ordered by leverage. Phase 1 is token and global-rule changes that
  improve every screen at once. Phase 3 is real layout work; do it last and one
  screen per commit.
- **Mobile must not change in Phase 3.** Every desktop layout below is added
  inside a `min-width` media query and must leave the phone UI pixel-identical.
- Do not touch the landing page beyond the short list in Phase 4.
- Gate for every commit:

  ```bash
  npm run lint
  npx tsc --noEmit
  npm test
  NEXT_PUBLIC_SUPABASE_URL=https://example.supabase.co NEXT_PUBLIC_SUPABASE_ANON_KEY=placeholder npm run build
  ```

### Seeing the signed-in app

Localhost cannot sign in, so visual checks need one of these:

1. A Vercel preview deployment of the branch or commit, where Google sign-in
   works. This is the reliable route.
2. Once signed in as the admin, demo mode (the `grind_demo_mode_pref=on` cookie;
   find its toggle via `useDemoMode`) fills Home, Leaderboard and friend profiles with fake

Check every visual change at 390, 768 and 1440 wide, in dark and light, and
with Reduce Motion on. If you cannot get a signed-in session, say so in the
report and mark the item "changed, not visually verified".

## Phase 1: tokens and global rules

### 1.1 Muted and secondary text fail contrast on cards (MEASURED, high)

`--text-muted` is the colour of bottom-nav labels, captions, chart ticks and
most small labels. It sits on three surfaces and passes WCAG AA (4.5:1 for small
text) on none of them:

| Token | On `--bg` | On `--surface` | On `--surface-elevated` |
| --- | --- | --- | --- |
| dark `--text-muted` `#7a7a7a` | 4.47 | 4.05 | 3.62 |
| dark `--text-secondary` `#888888` | 5.41 | 4.91 | 4.38 |
| light `--text-muted` `#656158` | 4.38 | 5.23 | passes |
| light `--danger` `#dc2626` | passes | 4.09 | not checked |

Fix, in `src/app/globals.css`. Each dark value is declared in three places:
the `@theme` block (lines 26–27), `:root` (81–82), and the `.share-card-dark`
pin (216–217). Change all three or the share card drifts.

| Token | Old | New | Result |
| --- | --- | --- | --- |
| dark `--text-muted` (and `--color-text-muted`) | `#7a7a7a` | `#8c8c8c` | 5.18 on surface, 4.62 on elevated |
| dark `--text-secondary` (and `--color-text-secondary`) | `#888888` | `#a3a3a3` | 6.15 on elevated |
| light `--text-muted` (line 148) | `#656158` | `#5c584f` | 5.03 on bg |
| light `--danger` (line 150) | `#dc2626` | `#b91c1c` | about 5.5 on surface; verify |

Secondary has to move with muted, otherwise the two become the same grey and
the hierarchy between them disappears.

Then update the palette line in `CLAUDE.md` (Design System) to the new values.
It currently lists muted as `#555555`, which is already out of date:
`#555555` is `--text-disabled` now.

This changes two documented brand greys. The shift is small (one step lighter)
but it is visible everywhere, so screenshot Home and Profile before and after
and show the owner if anything reads as washed out.

Verify with this, editing the pairs as needed:

### 1.3 The keyboard focus ring is invisible in light mode (MEASURED, high)

`globals.css:251`: `outline: 2px solid var(--accent) !important`. In light mode
`--accent` is `#a8c428`, which is 1.41:1 against the page and 1.68:1 against a
card. WCAG asks for 3:1 on a focus indicator. Dark mode is fine.

Fix: add a dedicated token so the ring can differ by theme.

```css
/* :root (dark), beside --accent-text */
--focus-ring: var(--accent);

/* html.light */
--focus-ring: var(--accent-text);   /* #4f6612, 4.60:1 on --bg */

/* .share-card-dark pin */
--focus-ring: #c8f135;
```

Then in the rule at line 251 use `outline: 2px solid var(--focus-ring) !important;`.
Grep `globals.css` for other `outline:` or focus `border-color: var(--accent)`
declarations (lines 4084, 4115, 4776, 4805, 4812, 6385, 6452 were flagged) and
decide for each whether it is a focus or selected state that needs the same
token in light mode.

**Done when:** in light mode, tabbing through Settings shows a clearly visible
olive ring on every control.

### 1.5 Dialogs are bottom sheets on desktop too (PLAUSIBLE, medium)

`src/components/ui/Dialog.tsx:209` sets `alignItems: 'flex-end'` inline on the
backdrop for every dialog at every width. On a 1440px monitor the completion
modal, plate calculator, exercise picker, rename dialog, body-weight editor and
add-photo sheet are 480px panels glued to the bottom edge of the screen. Only
`ConfirmDialog` overrides it (`style={{ alignItems: 'center' }}`).

Fix:

1. In `Dialog.tsx`, remove `alignItems: 'flex-end'` from the inline style and
   always add a base class to the backdrop, alongside the motion class:
   `className={['dlg-root', useDefaultMotion ? 'dlg-backdrop' : className].filter(Boolean).join(' ')}`.
   Add `dlg-sheet` to the panel when the caller did not pass `panelClassName`.
2. In `globals.css`, next to the existing `.dlg-*` rules (around line 843):

   ```css
   .dlg-root { align-items: flex-end; }

   @media (min-width: 768px) {
     .dlg-root { align-items: center; padding: 24px; }
     .dlg-root > .dlg-sheet {
       border-radius: var(--radius-lg) !important;
       max-height: min(88dvh, 760px);
       animation-name: dlg-pop-in;
     }
     .dlg-root[data-closing='true'] > .dlg-sheet { animation-name: dlg-pop-out; }
   }
   ```

   `ConfirmDialog`'s inline `alignItems: 'center'` still wins on mobile, so it
   is unaffected.
3. Read the `panelStyle` of all seven callers (`CompletionModal`,
   `ExercisePickerSheet`, `RenameExerciseDialog`, `BodyWeightCard`,
   `SettingsView`, `AddPhotoSheet`, `PlateCalculator`). Each was styled as a
   sheet: expect top-only corner radii and bottom safe-area padding. The
   `!important` radius above covers the corners; remove or neutralise any
   `env(safe-area-inset-bottom)` padding at ≥768px if it leaves a visibly
   uneven bottom margin.
4. Sheets that support swipe-to-dismiss (`useSwipeDismiss`) should keep working
   on touch tablets; do not remove the gesture, just confirm a centred panel
   still dismisses.

`html.reduce-motion` and the `prefers-reduced-motion` block already zero the
`.dlg-panel` animations; make sure the selectors there also match `.dlg-sheet`.

**Done when:** at 1440 wide each of the seven dialogs opens centred with four
rounded corners, and at 390 wide each is unchanged.

### 1.6 Hover states are wired with `onMouseEnter` (CONFIRMED, medium)

21 elements change opacity or background in `onMouseEnter` / `onMouseLeave`
handlers. Three problems: keyboard focus never triggers them, a tap on a touch
screen fires `mouseenter` and leaves the hover style stuck, and they bypass the
`(hover: hover)` guard the rest of the stylesheet uses.

Sites: `HomeDashboard.tsx` 1189, 1372, 1434, 1589, 1678 · `DaySelect.tsx` 357,
651, 743 · `log/past/page.tsx` 785, 966, 1293 · `WorkoutManager.tsx` 845, 862,
1293, 1448, 1463 · `ProfileDashboard.tsx` 713, 772 · `FriendProfileView.tsx`
343 · `FeedbackModal.tsx` 498 · `WorkoutCalendar.tsx` 368.

Fix: add two utilities to `globals.css` beside `.press`, then replace each
handler pair with the class and delete the inline base value it was toggling.

```css
/* Quiet icon buttons that brighten on hover or keyboard focus. */
.hover-reveal { opacity: 0.6; transition: opacity 150ms ease; }
.hover-reveal:focus-visible { opacity: 1; }
/* Rows and cards that lift to the elevated surface. */
.hover-surface { transition: background-color 150ms ease, border-color 150ms ease; }
@media (hover: hover) and (pointer: fine) {
  .hover-reveal:hover { opacity: 1; }
  .hover-surface:hover { background-color: var(--surface-elevated); }
}
```

Read each handler before replacing it: some set a border colour or a different
background, and `ProfileDashboard.tsx:772` sets React state (a tooltip), which
is a different case and should gain matching `onFocus` / `onBlur` instead.
Inline `backgroundColor` beats a class, so where `.hover-surface` is used the
resting background must move out of the inline style too.

Resting opacity goes from 0.4–0.5 to 0.6 on purpose: at 0.4 the edit and delete
icons in WorkoutManager are below 3:1.

## Phase 2: touch targets, labels and inputs

### 2.1 A shared hit-area utility (prerequisite for 2.2)

Several controls are deliberately small visually. Rather than redesign each,
extend the tappable area without changing the look:

```css
/* Extends the tap area to at least 44x44 without changing the visual size. */
.hit-44 { position: relative; }
.hit-44::after {
  content: '';
  position: absolute;
  top: 50%;
  left: 50%;
  width: max(100%, 44px);
  height: max(100%, 44px);
  transform: translate(-50%, -50%);
}
```

`hit-44` is not a Tailwind utility. A parent with `overflow: hidden` clips the
pseudo-element, which is fine: the target still grows as far as the parent
allows. Do not add it to two adjacent controls whose extended areas would
overlap; give those real size instead (see the rest-day pills).

## Phase 3: desktop layouts

The owner's standing rule is that desktop uses the full screen and is never a
stretched phone layout. Today only Home (`.home-grid`) and the live workout
(`.wo-layout`) have real desktop layouts. Everything else is one centred column:

| Screen | Container | Desktop width |
| --- | --- | --- |
| Progress | `page--progress` | 880px |
| Profile, Settings, friend profile | `page--profile` | 880px |
| Leaderboard, past log, progress photos | `page--narrow` | 640px |

All of Phase 3 is **PLAUSIBLE**: the structure was read from source but none of
these screens was seen. For each one, screenshot at 1440 before starting, build
it, and screenshot after. Rules for all of them:

- New CSS goes in `globals.css` inside `@media (min-width: 1024px)`, near the
  existing `.wo-layout` block. Mobile rules stay as they are.
- Use grid with named areas so the DOM order, and therefore the mobile layout
  and the tab order, does not change.
- No JS width detection (see Responsive navigation in `CLAUDE.md`).
- Each screen's `loading.tsx` skeleton must get the same grid, or the page will
  jump from one column to two when data arrives.
- The onboarding tours spotlight elements by `data-onboard` attribute. Keep
  every `data-onboard` on the same element it is on now.
